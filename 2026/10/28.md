# 1. 폴더 생성

```bash
mkdir kant-study
```

파일이나 폴더 이름에는 가능하면 공백을 사용하지 않는 것이 편하다.

예:


```text

_ = 언더스코어(underscore)
```

즉:

```text
kant-study
```

는 대시를 사용한 것이고,

```text
kant_study
```

`k`로 시작하는 파일과 폴더 모두 대상이 될 수 있다.

# 4. .gitignore

Git이 특정 파일이나 폴더를 추적 대상에서 제외하도록 설정하는 파일이다.

먼저:

```bash
touch .gitignore
```

`.gitignore` 파일을 만든다.

예를 들어:

```text
temp.dat
```

파일을 만들었다고 하자.

```bash
touch temp.dat
```

`.gitignore` 안에 다음 내용을 작성한다.

```gitignore
*.dat
```

그러면 `.dat` 확장자를 가진 파일들을 Git이 새로 추적하지 않는다.

예:

```text
temp.dat
user.dat
data.dat
```

모두 무시된다.

---

# 5. .gitignore를 사용하는 이유

대표적인 목적은 GitHub 등에 올릴 필요가 없는 파일을 제외하는 것이다.

예:

```text
비밀번호
API Key
환경설정 파일
개인정보
로그 파일
임시 파일
빌드 결과물
라이브러리 폴더
```

예를 들어:

```gitignore
.env
*.log
node_modules/
*.dat
```

처럼 사용할 수 있다.

## 중요

`.gitignore`는 단순히 보안용 파일만을 위한 것은 아니다.

Git으로 관리할 필요가 없는 파일을 제외하는 용도로 사용한다.

---

# 6. 이미 Git이 추적 중인 파일은 주의

`.gitignore`에 파일을 적었다고 해서 이미 Commit된 파일까지 자동으로 Git 관리에서 빠지는 것은 아니다.

예를 들어 이미:

```text
secret.env
```

를 Git이 추적하고 있다면:

```gitignore
secret.env
```

를 추가해도 계속 추적될 수 있다.

Git 추적만 제거하려면:

```bash
git rm --cached secret.env
```

그다음 Commit한다.

```bash
git commit -m "chore: stop tracking env file"
```

파일 자체는 로컬에 남아 있고 Git 추적만 제거된다.

# 7. Linux에서 파일과 디렉터리


하지만:

```text
폴더 = 일반 파일
```

이라고 완전히 동일하게 생각하는 것은 정확하지 않다.

디렉터리도 Unix/Linux에서는 **특수한 종류의 파일**로 취급된다고 이해하면 된다.

# 8. Git Remote 확인

현재 연결된 원격 저장소 확인:

```bash
git remote -v
```

예:

```text
origin  https://github.com/user/project.git (fetch)
origin  https://github.com/user/project.git (push)
```

---

# 9. 여러 Remote 등록

한 Git 저장소에 여러 Remote를 등록할 수 있다.

예:

```bash
git remote add origin GitHub주소
git remote add backup GitLab주소
```

확인:

```bash
git remote -v
```

예:

```text
origin  https://github.com/user/project.git
backup  https://gitlab.com/user/project.git
```

각각 따로 Push할 수도 있다.

```bash
git push origin main
```

```bash
git push backup main
```

`origin`, `backup`은 원격 저장소에 붙인 별명이다.

---

# 10. Remote 삭제

등록한 원격 저장소 연결을 삭제하려면:

```bash
git remote remove origin
```

또는:

```bash
git remote remove backup
```

이 명령어는 GitHub 저장소 자체를 삭제하는 것이 아니다.

로컬 Git에 등록되어 있던 **Remote 연결 정보만 삭제한다.**

# 11. Local과 Remote Commit 상태 확인

다음과 같이 나온다고 하자.

```bash
git log --oneline
```

결과:

```text
c009a72 (HEAD -> main) docs: Logs 폴더 제외
c310a46 (origin/main) feat: .gitignore 파일 생성
```

현재:

```text
HEAD -> main
```

은 로컬 `main` 브랜치가 `c009a72`를 가리키고 있다는 뜻이다.

반면:

```text
origin/main
```

은 마지막으로 알고 있는 원격 `main` 상태가 `c310a46`이라는 뜻이다.

즉 로컬에 새로운 Commit이 하나 더 있는 상태다.

```text
Local

c009a72 ← HEAD, main
   |
c310a46 ← origin/main
```

이 경우 일반적으로 아직 새 Commit을 Push하지 않은 상태다.

Push:

```bash
git push
```

후 같은 Commit을 가리키게 되면:

```text
c009a72 (HEAD -> main, origin/main) docs: Logs 폴더 제외
```

처럼 표시될 수 있다.

즉:

```text
HEAD -> main
origin/main
```

이 같은 Commit을 가리키면 로컬과 원격 브랜치 포인터가 같은 위치에 있다는 뜻이다.

# 12. git clone

```bash
git clone https://github.com/YS999900/kant-study.git
```

원격 Git 저장소를 내 컴퓨터로 복제한다.

정확히는 단순히 파일만 다운로드하는 것이 아니라:

```text
프로젝트 파일
+
Commit 기록
+
Branch 정보
+
Git 저장소 정보
+
origin Remote 설정
```

등을 함께 받아온다.

즉:

```text
Download
```

보다

```text
Git 저장소 복제
```

라고 이해하는 것이 정확하다.

일반적으로:

```bash
git clone 주소
```

를 실행하면 현재 위치 아래에 저장소 이름의 새 폴더가 만들어진다.

예:

```bash
git clone https://github.com/user/kant-study.git
```

결과:

```text
현재폴더/
└─ kant-study/
```

# 13. git clone과 git init 차이

내가 새로 만든 프로젝트:

```bash
git init
```

이미 존재하는 GitHub 프로젝트를 가져옴:

```bash
git clone 주소
```

쉽게:

```text
git init
→ 여기서 Git 관리를 새로 시작

git clone
→ 이미 존재하는 Git 저장소를 통째로 가져오기
```

`git clone`을 사용했다면 일반적으로 다시 `git init`할 필요가 없다.

```text
새로 추가된 파일
```

# 15. git add . 과 git add -A

```bash
git add .
```

현재 위치와 그 하위 경로를 기준으로 변경사항을 Stage에 올린다.

```bash
git add -A
```

Git 저장소 전체의 변경사항을 Stage에 올린다.

예:

```text
project/
├─ frontend/
│  └─ app.js
│
├─ backend/
│  └─ server.js
│
└─ README.md
```

현재 위치가:

```text
project/frontend/
```

일 때:

```bash
git add .
```

주로:

```text
frontend/ ✅
backend/ ❌
README.md ❌
```

반면:

```bash
git add -A
```

는:

```text
frontend/ ✅
backend/ ✅
README.md ✅
```

저장소 전체 변경사항을 대상으로 한다.

# 16. Commit Convention

Commit 메시지를 일정한 형식으로 작성하는 규칙을 Commit Convention이라고 한다.

대표적인 형식:

```text
type: 작업 내용
```

예:

```bash
git commit -m "docs: Git 명령어 정리"
```

자주 사용하는 Type:

| Type | 의미 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 |
| `style` | 코드 동작에 영향 없는 스타일 수정 |
| `refactor` | 기능 변화 없이 코드 구조 개선 |
| `test` | 테스트 코드 추가 및 수정 |
| `chore` | 설정, 패키지, 빌드 등의 기타 작업 |

```text
docs
```

# 19. git reset

Commit을 이전 상태로 되돌릴 때 사용할 수 있다.

대표적으로:

```text
--soft
--mixed
--hard
```

세 가지가 있다.

---

# 20. git reset --soft

```bash
git reset --soft 커밋ID
```

HEAD와 Branch를 지정한 Commit으로 이동한다.

이후 Commit들의 변경 내용은 **Stage에 남긴다.**

예:

```text
Commit 취소
↓
변경 내용은 Staging Area에 유지
```

즉 다시 Commit하기 쉬운 상태다.

---

# 21. git reset --mixed

```bash
git reset --mixed 커밋ID
```

HEAD와 Branch를 지정 Commit으로 이동한다.

변경 내용은 Stage에서 내려오지만 실제 파일에는 남아 있다.

```text
Commit 취소
↓
Stage 취소
↓
Working Directory에는 수정 내용 유지
```

`--mixed`는 `git reset`의 기본 동작이다.

즉:

```bash
git reset 커밋ID
```

는 기본적으로:

```bash
git reset --mixed 커밋ID
```

와 비슷하다.

---

# 22. git reset --hard

```bash
git reset --hard 커밋ID
```

HEAD와 Branch를 지정 Commit으로 이동하고 추적 중인 파일의 변경 내용도 해당 Commit 상태에 맞춘다.

즉:

```text
Commit 이동
+
Stage 변경 제거
+
Working Directory 변경 제거
```

## 주의

```bash
git reset --hard
```

는 작업 내용을 잃을 수 있으므로 매우 주의해서 사용한다.

---

# 23. reset 세 가지 비교

```text
              Commit   Stage   Working Directory

--soft          이동     유지        유지

--mixed         이동     해제        유지

--hard          이동     해제        되돌림
```

쉽게:

```text
soft
→ 다시 Commit하려고 할 때

mixed
→ 다시 수정하려고 할 때

hard
→ 변경 내용까지 버리고 완전히 돌아갈 때
```

---

# 24. git reflog

```bash
git reflog
```

HEAD와 Branch 등의 Reference가 어떻게 이동했는지 기록을 확인한다.

예:

```text
abc123 HEAD@{0}: reset: moving to ...
def456 HEAD@{1}: commit: docs: update Git
ghi789 HEAD@{2}: commit: feat: add login
```

## 중요

`reflog`가 **터미널에서 실행한 모든 명령어를 저장하는 것은 아니다.**

예를 들어:

```bash
ls
cd
mkdir
```

같은 모든 명령을 저장하는 것이 아니다.

Git의:

```text
Commit
Reset
Checkout
Merge
Rebase
```

등으로 인해 HEAD나 Branch가 이동한 기록을 확인하는 용도다.

---

# 25. Reset을 잘못했을 때 reflog 활용

예를 들어 실수로:

```bash
git reset --hard abc123
```

를 실행했다고 하자.

이전 HEAD 위치 확인:

```bash
git reflog
```

예:

```text
abc123 HEAD@{0}: reset: moving to abc123
def456 HEAD@{1}: commit: docs: update TIL
```

이전 상태로 돌아가고 싶다면:

```bash
git reset --hard HEAD@{1}
```

처럼 사용할 수 있다.

여기서:

```text
HEAD@{1}
```

은 reflog에 기록된 과거 HEAD 위치다.

# 26. Branch

Branch는 기존 작업을 유지하면서 별도의 작업 흐름을 만들기 위한 기능이다.

예:

```text
main
 |
 A
 |
 B
```

여기서 새로운 Branch를 만든다.

```text
main
 |
 A
 |
 B ← feature/login 생성
```

이후 `feature/login`에서 Commit하면:

```text
        C
       /
A ─── B
      ↑
     main
```

실제로는:

```text
main → B

feature/login → C
```

처럼 각각 다른 Commit을 가리키게 된다.

즉 Branch는 프로젝트를 통째로 복사하는 것이라기보다 **특정 Commit을 가리키는 가벼운 포인터**에 가깝다.

---

# 27. Branch 생성

```bash
git branch feature/login
```

`feature/login`이라는 이름의 Branch를 생성한다.

여기서:

```text
feature/login
```

의 `/`는 실제 폴더를 만드는 것이 아니다.

Branch 이름을 보기 좋게 구분하는 방식이다.

예:

```text
feature/login
feature/signup
fix/login-error
docs/readme
```

---

# 28. Branch 목록 확인

```bash
git branch
```

또는:

```bash
git branch --list
```

예:

```text
  feature/login
* main
```

`*`가 현재 위치한 Branch를 뜻한다.

## 잘못된 표현

```bash
git branch list
```

이 아니라:

```bash
git branch
```

또는:

```bash
git branch --list
```

를 사용한다.

# 29. Branch 이동

기존 방식:

```bash
git checkout feature/login
```

현재 HEAD를 `feature/login` Branch로 이동한다.

최근 Git에서는 역할이 더 명확한:

```bash
git switch feature/login
```

을 사용할 수도 있다.

즉:

```text
checkout / switch
→ 내가 작업할 Branch 이동
```

---

# 30. Branch 생성과 동시에 이동

기존 방식:

```bash
git checkout -b feature/login
```

의미:

```text
Branch 생성
+
새 Branch로 이동
```

최근 방식:

```bash
git switch -c feature/login
```

도 가능하다.

---

# 31. Branch 삭제

일반적인 삭제:

```bash
git branch -d feature/login
```

또는:

```bash
git branch --delete feature/login
```

병합되지 않은 Commit이 있으면 Git이 삭제를 막을 수 있다.

강제 삭제:

```bash
git branch -D feature/login
```

`-D`는 강제로 삭제하기 때문에 주의한다.

쉽게:

```text
-d
→ 안전하게 삭제

-D
→ 강제 삭제
```

# 32. Merge

Branch에서 작업한 내용을 다른 Branch에 합치는 것을 Merge라고 한다.

예:

```text
main
 |
 A ─ B
      \
       C ─ D
           ↑
     feature/login
```

`feature/login`의 작업을 `main`에 합치고 싶다면 먼저 `main`으로 이동한다.

```bash
git switch main
```

그다음:

```bash
git merge feature/login
```

뜻:

```text
feature/login의 변경사항을
현재 위치인 main에 합쳐라
```

## 중요

Merge는:

```bash
git merge 합칠브랜치
```

형식이다.

즉:

```text
현재 Branch
←
지정한 Branch를 가져와 병합
```

---

# 33. Merge 예시

먼저 확인:

```bash
git branch
```

현재:

```text
* main
  feature/login
```

이라면:

```bash
git merge feature/login
```

을 실행한다.

즉:

```text
feature/login
        ↓
       main
```

으로 합쳐진다.

---

# 34. Merge Conflict

두 Branch가 같은 파일의 같은 부분을 서로 다르게 수정했다면 Git이 자동으로 어느 것을 선택해야 할지 판단하지 못할 수 있다.

이를:

```text
Merge Conflict
```

라고 한다.

예:

```text
main
→ "로그인"

feature/login
→ "회원 로그인"
```

같은 줄을 서로 다르게 수정했다면 충돌할 수 있다.

이 경우 사람이 직접 어떤 내용을 사용할지 선택한 후:

```bash
git add .
git commit
```

등으로 Merge를 마무리한다.

# 38. 추가로 알아두면 좋은 명령어

현재 어느 Branch인지 확인:

```bash
git branch
```

현재 저장소 루트 확인:

```bash
git rev-parse --show-toplevel
```

Remote 확인:

```bash
git remote -v
```

Commit 그래프 보기:

```bash
git log --oneline --graph --all
```

Branch까지 같이 보면:

```bash
git log --oneline --graph --decorate --all
```

예:

```text
* a123456 (feature/login) feat: 로그인 추가
| * b234567 (main) docs: README 수정
|/
* c345678 initial commit
```

Branch를 배울 때 매우 유용하다.

# 39. 오늘 가장 중요한 개념

```text
.gitignore

→ 기존 Git 저장소 복제

→ Branch와 HEAD를 과거 Commit 방향으로 이동

→ HEAD 등의 이동 기록 확인

→ Branch 이동

git merge
→ 다른 Branch의 작업을 현재 Branch에 합치기
```
